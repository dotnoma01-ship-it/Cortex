## Safe import preparation plan (no import executed)

### Current product path and constraints

- The MongoDB `Product` model requires a unique `externalId`, `handle`, `type`, non-empty `variants` with numeric `price`, `stock`, and unique `sku`. Rating/reviews have defaults; imported sourcing records cannot be represented faithfully as store products until Cortex retail prices, available variants, stock policy, and identifiers are approved.
- `POST /api/products` is a single-product route protected by `protect` and `admin`. The current `normalize` allowlist does not accept `externalId`; the handler falls back to `Date.now()` when one is not supplied. Do not use this endpoint as an ad hoc bulk importer.
- `backend/src/scripts/seedProducts.js` reads the frontend JSON and upserts by handle using `$setOnInsert`. It does not replace an existing product matched by handle, but it is a database writer and must only be run in a controlled, approved environment after staging is complete.
- `GET /api/products` supports page-based pagination and returns `pagination { page, limit, total, pages }`; limit is capped at 100. `frontend/src/pages/Shop.tsx` currently calls `/products?limit=100` once. It will silently omit later pages when the remote catalogue exceeds 100.
- Detail lookup is by handle. The static JSON remains a browser fallback when API loading fails; cart/checkout rely on numeric variant prices and stock. Thus an import with placeholder prices or fake stock would affect purchase behaviour and is not safe.

### Proposed implementation before any production import

1. Add a separate admin-only bulk-import route, guarded by the existing JWT `protect` + `admin` middleware, strict request-size and batch-size limits, and an audit record. Do not reuse public enquiry or payment endpoints.
2. Require stable explicit `externalId`, handle, SKU, approved retail price, product type, validated variant identifiers/options, images with reuse approval, and an explicit inventory decision. Validate every row against Mongoose schema plus cross-row uniqueness before writing. Reject unknown fields and supplier-only cost data from the public Product schema.
3. Make the operation create-only by default. Detect duplicates by `externalId`, handle, and SKU, report each collision and skip it; never overwrite a current catalogue item. Keep supplier research in a separate staging record until mapped to approved storefront fields.
4. Provide a dry-run preview that returns normalized rows, create/skip/reject counts and row-level validation errors without a database write. Require a separate authenticated commit call referencing a batch digest/idempotency key; recheck duplicates at commit time to avoid race conditions.
5. Use a MongoDB transaction if the deployment topology supports transactions. If not, prevalidate the full batch, record the exact newly created document IDs, and on failure compensate by deleting only documents inserted by that batch. Persist a batch log with the input digest and per-row outcomes so operators can reconcile partial failure.
6. Add a controlled test database suite for authentication denial/approval, malformed rows, duplicate IDs/handles/SKUs, dry-run no-write, successful batch creation, and rollback/partial failure. No production execution until the route, test suite, approval of all import rows, and recovery procedure are reviewed.
7. Fix catalogue pagination without changing the page design: first either fetch all pages sequentially using `pagination.pages` and merge before the existing client-side filtering/sorting, or preferably extend the collection/search screens to use API pagination while preserving their current UI. Ensure filter, sort and search parameters are carried across pages and that page changes reset on filter changes. Add a test with more than 100 products to prove the full set is reachable.

No backend source, frontend storefront, or database was modified for this research update. The plan is documentation only; adding and testing an endpoint remains separate implementation work.
